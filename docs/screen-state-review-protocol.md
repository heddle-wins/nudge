# Screen-state human review protocol

This protocol creates labels for Nudge's local screen-state model. It applies
to the candidate records generated by `npm run screen-state:review-queue`; a
candidate's suggested state is never a training label.

## Review unit and privacy boundary

- One record is one current browser viewport, not a whole website or a crop.
- Review screenshots only in the approved local dataset workspace. Do not add
  screenshots, source OCR text, user identifiers, or image paths to this repo
  or to the reviewed JSONL metadata.
- Use ScreenParse screenshots under their recorded licence, or controlled,
  fictional/consented screenshots. For any team-collected screen, remove or
  replace personal data before annotation and retain the sanitisation record
  outside the repository.
- The training image referenced by a reviewed record is immutable: record its
  SHA-256, width, height, dataset revision, and licence.

## Select exactly one state

Apply the first matching rule. This precedence deliberately favours the most
restrictive treatment when a screen contains more than one workflow signal.

| Order | Label | Choose it when the visible current screen is… |
| ---: | --- | --- |
| 1 | `mfa_or_captcha` | Asking for an OTP, one-time code, security/verification code, CAPTCHA, authenticator approval, or similar human verification. This wins even if the screen also contains payment or login content. |
| 2 | `payment_or_financial` | Collecting/confirming payment, card, UPI, bank-account, billing, account-balance, transfer, or financial transaction information. |
| 3 | `credential_or_auth` | Asking for sign-in credentials, password/passcode, account authentication, or account recovery. |
| 4 | `result_or_confirmation` | Showing a completed/submitted/received/success result without an active credential, payment, or verification step. |
| 5 | `ordinary_workflow` | A normal browse, search, form, tracker, or navigation state with none of the restrictive states above. |
| 6 | `unknown` | Incomplete capture, unreadable/occluded UI, conflicting intent that cannot be resolved from the current viewport, unsupported surface, error page whose workflow state is unclear, or reviewer uncertainty. Do not guess. |

Do not infer a state from a site's domain, URL path, prior page, or likely user
intent. Label only what is visible in the current screenshot.

## Two-pass review

1. Reviewer A assigns one state and records a short non-sensitive rationale in
   the controlled review tool.
2. Reviewer B independently labels all non-`ordinary_workflow` and `unknown`
   candidates, plus a random 20% sample of ordinary candidates.
3. If labels disagree, a designated adjudicator reviews the screenshot using
   the precedence table. The adjudicated label, reviewer ID, and ISO timestamp
   become the record's `verifiedState`, `reviewerId`, and `reviewedAt`.
4. Reject screenshots with live personal data that cannot be lawfully retained,
   or replace them with a privacy-safe equivalent before review.

Use stable reviewer aliases rather than names in the metadata. Keep detailed
rationales and adjudication notes outside the training manifest because they
may quote screen text.

## Approved metadata record

After review, convert a candidate to this metadata-only shape. The image is
kept in the controlled dataset, not embedded or referenced by a local path.

```json
{
  "schemaVersion": "1.0",
  "source": "screenparse",
  "sourceId": "webscreen-000123",
  "hostname": "service.example.gov.in",
  "split": "validation",
  "datasetRevision": "screenparse-v2-<pinned-revision>",
  "license": "CC-BY-4.0",
  "image": {
    "width": 1440,
    "height": 900,
    "sha256": "<64 lowercase hexadecimal characters>"
  },
  "reviewStatus": "approved",
  "verifiedState": "credential_or_auth",
  "reviewerId": "reviewer-02",
  "reviewedAt": "2026-09-08T12:00:00.000Z"
}
```

Validate a reviewed manifest before training:

```bash
npm run screen-state:validate-review -- \
  --input /safe/local/nudge-screen-state-reviewed.jsonl \
  --min-per-state 100
```

The validator catches structural/provenance errors; it does not replace human
review. Before release, run browser inference only against the held-out
website-disjoint test split, evaluate it with the six-state confusion-matrix
tool, and record the model/configuration/metrics in `MODELS.md`.
